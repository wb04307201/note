## 一、为什么「数据倾斜」是个危险的模糊词

「数据倾斜」在分库分表语境下是一个**被严重混用的词**。它至少同时指两件成因、度量、解法完全不同的事：

| | 数据量倾斜 | 访问量倾斜（热点） |
|---|---|---|
| 不均的是什么 | **存储**：各分片行数/容量不均 | **请求**：各分片 QPS/负载不均 |
| 典型解法 | 换分片键、复合分片、大户独立路由 | 缓存、限流、热点探测 + 动态路由 |

混用直接导致三类工程误判：

1. **对热点做扩容**：某明星用户订单查询打爆单分片（访问量倾斜），团队却启动分片翻倍迁移——存储本来就没不均，扩容后请求照样集中在新路由的那个分片，白付一次全量迁移。
2. **对高基数键做二次打散**：user_id 分片已经很均匀，有人看到「倾斜」告警（其实是热点告警）后给分片键再叠一层打散/加盐——单用户查询从「单分片命中」退化为「多分片扇出」，把最宝贵的查询局部性毁掉了。
3. **把发布手段当倾斜解法**：把「先归档再扩容」（这是数据量增长的常规操作，见 [父文件扩容节](../README.md)）当作倾斜治理方案汇报，掩盖了真正的问题类型。

所以本文的第一原则：**任何倾斜工单/告警/方案，先回答"不均的是存储还是请求"**，再谈解法。

## 二、两类倾斜的对比与度量

### 2.1 定义与成因

- **数据量倾斜**：数据写入/存量分布不均。成因是分片键选择不当（低基数、业务偏斜）或个别实体天然巨大（超级大户）。它是**慢性问题**——随存量累积显现，恶化以周/月计。
- **访问量倾斜**：请求分布不均。成因是业务天然头部效应（爆款商品、明星用户、大 V 动态、秒杀）。它是**急性问题**——随活动/事件瞬时爆发，恶化以秒/分钟计，且**与数据分布是否均匀无关**。

访问量倾斜还要再分一层，因为读写解法不同：

- **读热点**：爆款详情页、明星动态——可缓存性好，主战场是第四节的缓存分层与副本扩展；
- **写热点**：秒杀库存扣减、大 V 发文下的评论写入——缓存帮不上忙（写必须落库），解法方向是请求合并/排队削峰（把并发写串行化或批量落库）、或对单实体再拆桶（库存拆成 N 个子桶分摊行锁），本质是「让写慢下来或散开」，而不是「让写更快」。

两者的探测信号也不同：读热点看 QPS top-k，写热点看**行锁等待与单分片写 TPS**——只监控读 QPS 会漏掉写热点。

### 2.2 度量指标（先埋点，再谈治理）

| 维度 | 数据量倾斜 | 访问量倾斜 |
|------|-----------|-----------|
| 核心指标 | 各分片行数、单分片磁盘占用 | 各分片 QPS / TPS、单分片连接数 |
| 不均度量化 | 最大分片 / 最小分片的行数比 | 最热分片 QPS / 分片均值 QPS |
| 辅助信号 | 单分片表空间增长率、最大单实体（用户/租户）行数 | 慢查询在分片维度的分布、DB CPU/IO 在分片维度的离散度 |
| 探测手段 | 定时对账任务扫 `information_schema` 行数/容量 | 热点 key 探测（滑动窗口 top-k）、接入层按分片键采样计数 |

**告警阈值口径**（以下为**示例阈值**，用于说明口径，不是生产实测数字，落地时按自身容量压测标定）：

- 数据量倾斜：最大/最小分片行数比持续超过某个倍数（示例阈值：> 1.5 观察、> 2 介入），或单分片容量达到水位线（示例阈值：80%）而其他分片远未达到。
- 访问量倾斜：单分片 QPS 达到均值的某个倍数（示例阈值：> 3 倍触发热点探测复核），或单分片慢查询占比与其流量占比显著背离。

### 2.3 为什么高基数离散键几乎不产生数据量倾斜

这是本文最容易被忽略的论断：**user_id / order_id / uuid 这类高基数离散键做 hash 分片时，数据量倾斜几乎不发生**。论证靠大数定律，分两步说清（注意是「期望均匀 + 方差相对收敛」，不是「绝对均匀」）：

1. **期望均匀**：键空间（如 10⁹ 量级的 user_id）远大于分片数（如 2⁴~2⁸），且键值分布无业务偏斜（注册顺序、hash 后近似独立同分布）时，每条数据落入任一分片的概率均为 1/N，各分片行数的**期望值相等**。
2. **方差相对收敛**：分片行数近似多项分布，单分片行数的标准差量级为 √n（n 为该分片期望行数），**相对偏差 ≈ 1/√n**。做个量级示意（**示例推演**，非生产实测）：某分片期望 1000 万行时 √n ≈ 3162，相对偏差约 0.03%——即使实际多几千行，在容量维度上完全不可见；而当 n 只有 1 万时相对偏差升到 1%，才开始值得看。也就是说，**数据量倾斜在高基数键 + 大样本下是数学上被压制的，不是靠运维努力压制的**。

反例恰好验证了条件：**低基数键**（region、status、tenant_id）的键空间小于或接近分片数，大数定律的前提不成立——每个键背后的数据量本身就是巨样本且彼此悬殊（如 status=已完成 的行数天然是 status=退款中 的百倍以上），hash 只是把「键本身的不均」原样搬进分片，**必然不均**。

> 推论：对高基数键分片出现的「倾斜」告警，几乎一定是访问量倾斜被误报/混报——回到第一节先分型。

## 三、数据量倾斜的三类成因与对症解法

### 3.1 成因①：分片键低基数 → 复合分片键 / 二级散列

低基数键（tenant_id、region、channel）单独做分片键，键空间撑不满分片数。对症解法是**复合分片键**：用低基数键定粗粒度位置（保住它的路由语义），再叠一个高基数键做二级散列填满容量。

典型设计：`hash(tenant_id) 定库 + hash(order_id) 定表`：

```java
// 复合分片键路由：tenant_id 定库（保住租户隔离/按租户查询的路由语义），
// order_id 定表（高基数键填满表级容量，消除库内数据量倾斜）
public ShardLocation route(long tenantId, long orderId) {
    int dbIndex    = (int) (Math.floorMod(tenantId, DB_COUNT));     // 如 4 库
    int tableIndex = (int) (Math.floorMod(orderId, TABLE_COUNT));   // 如每库 8 表
    return new ShardLocation("ds_" + dbIndex, "t_order_" + tableIndex);
}
```

路由收益分级：

- 按 `(tenant_id, order_id)` 查 → 单库单表，最优。
- 只按 `tenant_id` 查 → 单库 8 表扇出，可接受（租户维度查询天然限定在一个库内）。
- 只按 `order_id` 查 → 库位置未知，需 4 库各查 1 张确定的表（4 次而非 32 次全扫）；若此场景高频，考虑 [基因法](#五基因法gene-method让两个键路由到同一分片) 或异构索引表。

❌ **反模式：低基数键倾斜了就扩容**。扩容不改变键到分片的映射不均——4 库扩 8 库，status=已完成 的数据照样挤在同 hash 槽对应的分片里，**不均被等比放大**而非消除。扩容解决的是「总量超容量」，不是「分布不均」。

### 3.2 成因②：超级大户 / 头部租户 → 大户独立路由

B 端场景（SaaS、商家平台）的经典问题：tenant_id 基数不低，但**单个头部租户的数据量是长尾租户的成千上万倍**——这是「键值本身巨大」，hash 再均匀也无解。对症解法：

- **VIP 分片 + 名单驱动路由**：维护一张「大户名单」表（或配置中心），路由层先查名单——名单内的大户各自独占一个分片（甚至独立实例），名单外走常规 hash。

```java
public ShardLocation routeTenant(long tenantId) {
    Long vipShard = vipRoutingTable.get(tenantId);   // 名单驱动（本地缓存 + 定期刷新）
    if (vipShard != null) {
        return ShardLocation.of("ds_vip_" + vipShard); // 大户独立路由
    }
    return ShardLocation.of("ds_" + Math.floorMod(tenantId, SHARD_COUNT)); // 常规 hash
}
```

- **按数据量分级的差异化策略**：大户库内部可再按时间/订单号二级分表；长尾租户合库合表。即「一个租户一个策略」的分级容量规划。

**成本讨论（名单维护 vs 倾斜收益）**：VIP 名单是**人肉/半自动运维资产**——晋升（长尾长成大户）、降级（大户萎缩）、迁移窗口都要流程化。经验口径：头部租户贡献了绝大部分数据量或营收时才值得建名单机制；若头部效应不明显，名单维护成本会超过倾斜本身的损失，不如保持纯 hash。

❌ **反模式：给所有租户按数据量动态重分片**。没有名单的显式语义，靠系统自动感知「谁大了就给谁挪」，会引入不可预测的迁移风暴——大户路由必须是**显式、可审计的决策**，不是自动行为。

### 3.3 成因③：历史长尾集中 → 冷热分离 + 归档

时间相关分片（按月/按 ID 区间）的必然形态：最新分片持续膨胀、历史分片只读且巨大。这不是路由错误，是**数据生命周期问题**——对症解法是归档而非改路由：热数据留在线分片，冷数据压缩归档到廉价存储，在线分片体量自然回落。

完整方案（归档判定、双存储架构、回查通道）见 → [冷热数据分离](../../cold-hot-data-separation/README.md)，此处不复述。父文件的[扩容节](../README.md)也已给出「扩容前先归档，可能根本不需要扩容」的生产建议。

❌ **反模式：用扩容承接历史长尾**。历史数据只读、增长已停止，为它扩在线分片是给死数据付活数据的成本。

## 四、访问量倾斜（热点）的分层治理

访问量倾斜的正确心智：**它不是数据库问题，是全链路流量分配问题**。数据层拆分是最后手段，绝大多数热点应该死在离用户更近的层。

### 4.1 分层手段表（从外到内，逐层拦截）

| 层 | 手段 | 拦截什么 | 深链 |
|----|------|---------|------|
| ① 客户端/接入层 | 限流、排队、请求合并 | 超出系统容量的部分直接削掉 | [限流](../../../../../12.interview/04.system-design/rate-limiting/README.md) |
| ② CDN / 浏览器缓存 | 静态化、边缘缓存 | 可静态化的热点内容根本不到源站 | [CDN](../../../cdn/README.md) |
| ③ 应用 L1 本地缓存 | Caffeine 等进程内缓存 | 单 key 高并发读，进程内消化 | [全链路缓存分层](../../../cache-layers/README.md) |
| ④ 分布式缓存 L2 | Redis 集群读扩展 | 跨实例共享的热点读 | 同上 |
| ⑤ 读副本扩展 | 热点分片加从库分摊读 | 缓存未命中的读流量 | [读写分离](../../read-write-splitting/README.md) |
| ⑥ 热点分片独立部署 | 热 key 迁到独立缓存/DB 实例 | 隔离爆炸半径，保护其余分片 | 见 4.2 动态路由 |
| ⑦ 数据层拆分 | 热点实体再分片（如大 V 粉丝表拆桶） | 单实体写热点（最后手段） | — |

> 分工说明：缓存各层的命中语义、失效机制与一致性代价在 [全链路缓存分层](../../../cache-layers/README.md) 已系统展开；本文只负责「热点如何被逐层拦截」的调度视角。单节点热点 Key 的面试版打法（本地缓存 + 互斥重建话术）见 → [`缓存热点 Key`](../../../../../12.interview/04.system-design/cache-hot-key/README.md)。

### 4.2 热点探测机制

治理前提是**知道热的是谁**。三条探测通路互补：

1. **实时统计（主通路）**：接入层/应用层对分片键做滑动窗口计数，维护 top-k 热 key（窗口秒级~分钟级；计数结构可用 Redis ZSET 精确 top-k，或 Count-Min Sketch 近似省内存）。

```text
滑动窗口 top-k 探测（伪代码）：
  每个请求经过接入层/DAO 拦截器时：
    bucket = floor(now / windowSize)            # 当前时间桶
    key    = 分片键值（如 user_id / item_id）
    INCR  counter[bucket][key]                  # Redis: ZINCRBY hot:{bucket} 1 {key}
    EXPIRE counter[bucket] 2*windowSize         # 桶自动过期，天然滑动
  探测任务（每 windowSize 触发）：
    topK = ZREVRANGE hot:{bucket} 0 K-1 WITHSCORES   # 精确 top-k
    for (key, count) in topK:
      if count / totalRequests > hotThreshold:        # 示例阈值，压测标定
        emitHotKeyEvent(key, count)                   # 触发动态路由/预热/限流降级
```

2. **DB 侧指标反推（兜底通路）**：慢查询日志、分片维度的 CPU/IO/连接数离散度——当探测通路自身被热点打挂或漏报时，DB 的异常分布是最后的信号源。
3. **客户端/业务上报（事件通路）**：大促、明星事件是**可预知的热点**——运营侧提前报备比任何实时探测都快，直接预热。

**探测到热点后的动态路由**：把热 key 从常规路由摘出，指向独立的热点分片/独立缓存集群——常规分片立刻卸压，热点爆炸半径被隔离在专用资源内。

**回落机制（同样关键）**：热度下降后必须把 key 迁回常规路由并释放热点资源，否则热点分片只增不减——长期碎片化，容量规划失真，最终「热点集群」变成没人敢动的第二套主库。回落判据用滞回区间（示例口径：热度低于迁出阈值一段时间后自动迁回，迁出/迁回阈值取不同值防抖动），迁回过程走与迁出相同的「先双写/先预热再切读」流程。

### 4.3 缓存兜底的失效风险

热点治理重度依赖缓存，而缓存恰恰在**最热的时候最危险**：热点 key 缓存失效瞬间，全部请求穿透到 DB 单分片——这就是缓存击穿，在热点场景下等价于「把访问量倾斜原样砸向最脆弱的一层」。必须配套：

- **互斥重建**：只放一个请求回源重建，其余等待；
- **逻辑过期**：value 带过期时间戳，物理不过期，异步刷新。

完整机制（穿透/击穿/雪崩三件套的区分与解法）→ [缓存穿透 / 击穿 / 雪崩](../../../../../12.interview/03.database/cache-penetration-breakdown-avalanche/README.md)，此处不复述。

## 五、基因法（Gene Method）：让两个键路由到同一分片

### 5.1 问题定义

订单表按 `user_id % N` 分片（买家查订单列表是主场景）。但支付回调、物流推送等链路**只有 order_id**——按 user_id 的路由规则无法定位分片，只剩两条烂路：

- 全分片扫描（N 次查询，浪费且慢）；
- 建 `order_id → user_id` 映射表（多一次查询 + 一个需要保证一致性的额外存储）。

三条路线的对比：

| 方案 | 查 order_id 的开销 | 额外存储 | 一致性负担 | 扩容自由度 |
|------|------------------|---------|-----------|-----------|
| 全分片扫描 | N 次查询取并集 | 无 | 无 | 高 |
| 映射表 | 1 次映射查询 + 1 次分片查询 | 映射表本身也要分片（通常按 order_id） | 订单与映射双写一致（需事务/对账） | 高（映射表可独立重建） |
| 基因法 | 1 次分片查询（最优） | 无 | 无 | **低（模数固化，见 5.5）** |

基因法的本质是**把路由信息前置固化进 ID**，用「生成时多算一步」换「查询时零额外开销」——代价全部押在扩容自由度上。

### 5.2 解法原理

**在生成 order_id 时，把 user_id 的分片位（"基因"）嵌进 order_id 的低位**，使：

```text
order_id % shardCount == user_id % shardCount
```

之后无论拿到哪个键，`% shardCount` 都路由到同一分片——order_id 天生"记得"自己属于哪个 user 的分片。

### 5.3 实现一：位运算嵌基因（要求 shardCount 是 2 的幂）

```java
public class GeneIdGenerator {
    private static final int SHARD_COUNT = 8;             // 必须是 2 的幂
    private static final int GENE_BITS   = 3;             // log2(8) = 3
    private static final long GENE_MASK  = SHARD_COUNT - 1; // 0b111

    /** 生成带基因的 order_id：seq 左移腾出低 3 位，填入 user_id 的分片位 */
    public static long genOrderId(long seq, long userId) {
        long gene = userId & GENE_MASK;                   // user_id 的分片位
        return (seq << GENE_BITS) | gene;
    }

    /** 任意键（userId 或 orderId）取分片：都只看低位 */
    public static int shardOf(long key) {
        return (int) (key & GENE_MASK);
    }
}
```

**验证片段（实际推演）**：

```java
public static void main(String[] args) {
    long userId  = 100L;                                  // 100 % 8 = 4
    long orderId = GeneIdGenerator.genOrderId(12345L, userId);
    // orderId = (12345 << 3) | (100 & 7) = 98760 | 4 = 98764
    System.out.println(orderId);                          // 98764
    System.out.println(GeneIdGenerator.shardOf(userId));  // 4
    System.out.println(GeneIdGenerator.shardOf(orderId)); // 98764 & 7 = 4 ✓ 同分片
}
```

推演确认：`12345 << 3 = 98760`（低 3 位必为 0），`| 4` 后低 3 位恰为基因 4，故 `98764 & 7 == 100 & 7 == 4`。**等式成立的充要条件**是 shardCount 为 2 的幂——此时 `% N` 与 `& (N-1)` 等价，且左移不会污染基因位。

### 5.4 实现二：乘模嵌基因（不要求 2 的幂）

```java
public static long genOrderId(long seq, long userId, int shardCount) {
    long gene = Math.floorMod(userId, shardCount);   // 基因 ∈ [0, shardCount)
    return seq * shardCount + gene;                  // orderId ≡ gene (mod shardCount)
}

public static int shardOf(long key, int shardCount) {
    return (int) Math.floorMod(key, shardCount);     // floorMod 防负数键的符号坑
}
```

**验证片段（实际推演）**：

```java
int shardCount = 6;                                    // 故意取非 2 的幂
long userId  = 100L;                                   // 100 % 6 = 4
long orderId = genOrderId(12345L, userId, shardCount);
// orderId = 12345 * 6 + 4 = 74074
System.out.println(shardOf(userId, 6));                // 4
System.out.println(shardOf(orderId, 6));               // 74074 % 6 = 4 ✓
// 74074 = 6 × 12345 + 4，被 shardCount 整除的部分不带余数，余数即基因
```

两种写法等价于同一个同余式 `orderId ≡ userId (mod shardCount)`；写法①用位运算更快但锁死 2 的幂，写法②通用但乘法占用 ID 值域更多。

### 5.5 代价与边界（决定要不要用的部分）

1. **基因位挤占 ID 空间**：写法①中 seq 被左移 GENE_BITS 位，同等位宽下可容纳的序列数缩小为 1/2^GENE_BITS；写法②中 orderId 值域放大 shardCount 倍。64 位 long 下通常仍够用，但必须做进 ID 位段预算。
2. **分片数一旦确定，几乎不可改**——这是最大代价。基因只携带 `% 8` 的信息：若扩容到 16 并按 `% 16` 路由，上例 userId=100 → `100 % 16 = 4`，而旧 orderId=98764 → `98764 % 16 = 12`，**同分片等价性被破坏**（3 位基因无法区分 %16 下的 {4, 12}）。因此基因法方案下扩容只有两条路：路由模数保持 8 不变（新库作为逻辑组挂在原模数下），或对存量 ID 重建映射。这也是「分片数选 2 的幂」的另一层理由——翻倍后至少模数兼容的路径还存在（配合父文件的 [翻倍扩容流程](../README.md)，本文不复述步骤）。
3. **只适用于「两键必须同分片」的场景**：user_id ↔ order_id 这类强关联键对。滥用见反模式清单。
4. **与雪花 ID 的位段冲突**：Snowflake 的低位是 sequence、中间是机器位——基因嵌入必须与 ID 方案的位段规划**统一设计**（改哪几位、seq 容量损失多少），不能各自为政。分布式 ID 方案对比 → [分布式 ID](../../../../02-distributed/distributed-id/README.md)。

## 六、反模式清单

| # | 现象 | 为什么错 | 正确做法 |
|---|------|---------|---------|
| 1 | 听到「倾斜」就上扩容/迁移 | 没辨析数据量 vs 访问量——扩容只对「总量超容量」有效，对分布不均（低基数键）和请求热点都无效 | 先看第二节度量指标定位倾斜类型，再选第三节/第四节解法 |
| 2 | 对 user_id 分片做二次打散 | 高基数键数据量本就均匀（大数定律），打散毁掉单用户查询的单分片局部性，所有查询变扇出 | 高基数键的「倾斜」告警按访问量倾斜排查（热点探测），不动路由 |
| 3 | 分片键选低基数字段 | 键空间 < 分片数，hash 只是搬运键值本身的不均，必然数据量倾斜 | 低基数键只做复合分片键的粗粒度层（定库），高基数键做二级散列（定表） |
| 4 | 热点只加缓存，不做探测与限流 | 缓存失效瞬间击穿流量原样砸向 DB 单分片；没有探测就永远在事后救火 | 缓存 + 互斥重建/逻辑过期 + 滑动窗口探测 + 接入层限流四件套齐上 |
| 5 | 基因法滥用于不需要同分片的键对 | 白白把分片数锁死（基因模数固化），付出扩容自由度却换不到路由收益 | 先确认「两个键高频互查且都需单分片命中」，再上基因法；否则映射表/异构索引更灵活 |
| 6 | 热点分片只迁不回收 | 热度回落后资源不释放，热点集群长期碎片化，容量规划失真 | 滞回区间判定热度回落，自动走「预热→切读→迁回」回收流程 |
| 7 | 分片数不是 2 的幂 | 翻倍扩容失去模数兼容路径；基因法只能用乘模写法且值域膨胀更明显 | 分片数取 2 的幂（4/8/16/32），与父文件扩容节的翻倍策略对齐 |

## 七、落地检查清单（上线前 review）

- [ ] **分片键基数评估**：键空间 / 分片数 ≫ 1？有无单键值巨大（大户）的可能？低基数键是否只用作复合键粗粒度层？
- [ ] **倾斜度量已埋点**：分片行数/容量对账任务 + 分片维度 QPS/慢查询分布，两类指标分开告警（不共用「倾斜」一个名字）。
- [ ] **大户路由预案**：VIP 名单机制是否需要？晋升/降级/迁移流程是否显式可审计？
- [ ] **热点探测与限流就位**：滑动窗口 top-k 探测、可预知热点的报备预热通道、接入层限流阈值。
- [ ] **缓存兜底防击穿**：热点 key 的互斥重建/逻辑过期策略已配置并演练过失效场景。
- [ ] **分片数是 2 的幂**：与翻倍扩容策略、基因法位运算写法兼容。
- [ ] **扩容预案验证过**：在预发环境完整演练过一轮（流程细节见[父文件扩容节](../README.md)），基因法场景额外验证模数兼容性。
- [ ] **基因位与 ID 方案统一规划**：位段分配文档化，seq 容量损失已评估，与分布式 ID 生成器同一次设计定稿。
