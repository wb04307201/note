# 相似文档消歧（Similar Doc Disambiguation）

> ⬅️ [返回 L2 技术栈](../README.md)

> **一句话定位**：同一实体在**不同时间 / 版本 / 规格**下的多条高度相似文档，是 RAG 检索的系统性盲区——**Rerank 排不掉**（它是精度增强，不是事实仲裁），必须把「**语义模糊匹配**」与「**属性精确匹配**」解耦：向量模型理解"意思"，元数据过滤 / 混合检索 / 意图澄清 / 结构化分块死磕"数字、时间、版本"。

---

## 🎯 问题：合理的"相似脏数据"

### 例子 1：时序数据（时间维度差异）

> **用户 Query**："A项目目前的应收账款余额是多少？"
> **Doc 1**："截至 **2026年11月**，A项目的应收账款余额为 **120万元**。"
> **Doc 2**："截至 **2026年12月**，A项目的应收账款余额为 **1200万元**。"

**业务合理性**：同一项目不同月份余额不同，完全合法。用户问"目前"，期望得到最新（12月）的数据——但 Doc 1（11月）会被误当答案。

### 例子 2：多规格 / 多版本（条件维度差异）

> **用户 Query**："Model X 的最大续航里程是多少？"
> **Doc 1**："Model X **标准续航版**的最大续航里程为 **550公里**。"
> **Doc 2**："Model X **长续航版**的最大续航里程为 **720公里**。"

**业务合理性**：同一产品多配置参数不同，完全合法。用户没指定版本，系统要么判断给哪个、要么把两个都列出来。

**共性**：这不是脏数据，是**合法的多条近重复事实**——检索目标是"精准区分"，不是"排掉一条了事"。

---

## 🔬 为什么 Rerank 排不掉

以例子 1 为例，BGE-Reranker 类模型计算 Query 与 Doc 1/Doc 2 相似度时：

1. **语义平滑效应**：Reranker 擅长"大局"——Doc 1 和 Doc 2 都在回答"A项目的应收账款"，全局语义匹配度都极高
2. **细粒度实体不敏感**："11月 vs 12月"、"120万 vs 1200万"在注意力空间的距离，远小于"应收账款 vs 余额"这类主题词的距离
3. **分数无判别意义**：Doc 1 打 0.92、Doc 2 打 0.93（**示意口径**）——模型无法识别"12月 = 目前"，Doc 1 留在 Top-K 中误导生成

> **Rerank 的定位**：把语义相关的排更前（精度增强）；**不是**判定哪条事实符合约束（事实仲裁）。同主题不同质量 → Rerank 有效；同质量不同属性 → Rerank 无判别力。成本上 Rerank +10ms 不一定值得（见 [Reranker](../reranker/README.md)），指望它解决属性级歧义是用错工具。

## 🛠️ 四类工程解法（语义 / 属性解耦）

**总原则**：把需要精确匹配的"刺头"属性（数字 / 时间 / 版本 / 编号），从非结构化文本中剥离，交给结构化或字面手段；向量只负责语义。

### 方案 1：元数据过滤（Metadata Filtering）——最推荐的"降维打击"

1. **入库时**：LLM 或正则提取结构化元数据
   - Doc 1 → `{"project": "A", "time": "2026-11", "amount": 120}`
   - Doc 2 → `{"project": "A", "time": "2026-12", "amount": 1200}`
2. **检索前**：LLM / 规则把"目前"解析为具体条件（`time >= 2026-12` 或 `time == latest`）
3. **执行**：向量检索**前**硬过滤（Pre-filtering）——11 月数据不进候选，只对 12 月数据算相似度

- 库内下推实现：Milvus `AnnSearchRequest(expr=...)` / ES filter，见 [Hybrid Search §生产要点](../hybrid-search/README.md)
- 元数据入库流水线（解析参数 / 溯源字段）：见 [Knowledge Ingestion Pipeline §元数据](../knowledge-ingestion-pipeline/README.md)

### 方案 2：混合检索（向量 + BM25 字面兜底）

- Query 含精确属性词时（"2026年12月"），BM25 给 Doc 2 极高字面分、Doc 1 低分；RRF 融合后 Doc 2 稳定靠前
- **边界**："目前"是**相对时间**，字面上没有"12月"——BM25 同样救不了，必须先走方案 1 把相对时间解析为绝对条件
- 融合机制与调优：见 [Hybrid Search](../hybrid-search/README.md)

### 方案 3：Query 改写与意图澄清（意图本身缺失时）

- **意图识别**：轻量 LLM 前置判断——用户问"Model X 续航"没说是标准版还是长续航版，歧义在**问题侧**
- **策略 A · 多路改写**：拆成"Model X 标准续航版 续航" / "Model X 长续航版 续航"分别检索，生成端综合列出
- **策略 B · 反问**：直接问用户要哪个版本——意图缺失时，正确答案是"反问"而不是检索
- 改写手段全景：见 [Query Rewrite](../query-rewrite/README.md)

### 方案 4：Chunk 切分优化（自包含事实）

- **失效根因之一**：Chunk 切太长，把"标准版"和"长续航版"参数混在一个 Chunk 里，Rerank 看到的是"混杂事实"
- **做法**：基于文档结构（Markdown / HTML）或语义切分，保证每 Chunk = **自包含完整事实 + 上下文标题**，如 `[Model X 标准续航版] 最大续航里程为 550公里`
- 切分策略全景：见 [Chunking Strategies](../chunking-strategies/README.md)

### 选型对照

| 方案 | 解决的歧义类型 | 成本 | 局限 |
|------|--------------|------|------|
| 元数据过滤 | 时间 / 版本 / 规格等**可结构化属性** | 入库抽取成本 | 属性提不全就漏 |
| 混合检索 | query **含精确属性词** | 低（BM25 基建已有） | 相对时间（"目前"）无效 |
| Query 澄清 | **用户意图本身缺失** | LLM 调用 + 延迟 | 高频场景反问伤体验 |
| Chunk 优化 | 切分粒度混杂 | 重建索引 | 治标，兜不住检索侧歧义 |

## 📐 如何度量消歧效果（R1）

| 指标 | 公式 | 在消歧场景的含义 |
|------|------|----------------|
| **NDCG@K** | $DCG@K = \sum_{i=1}^{K} \frac{2^{rel_i}-1}{\log_2(i+1)}$，$NDCG = \frac{DCG@K}{IDCG@K}$ | 正确版本（12月 / 长续航版）是否排在 Top-K 前部；$rel$ 按"属性符合约束"打分 |
| **MRR** | $MRR = \frac{1}{rank_{\text{first relevant}}}$ | 第一条"属性正确"的文档排第几——消歧任务最直观的口径 |

**用法**：构建黄金集（query + 标注"哪条是当前版本"），对比上线前 NDCG@K / MRR——"Rerank 前后"在消歧场景通常**无提升**（这正是盲区的证据），加元数据过滤后应显著提升。

## ⚠️ 反直觉

| 误区 | 真相 |
|------|------|
| ❌ Rerank 能排除错误数据 | ✅ 精度增强 ≠ 事实仲裁，属性级歧义排不掉（0.92 vs 0.93 无判别意义） |
| ❌ 多版本是脏数据，清洗掉就好 | ✅ 时序/多规格并存是**合法业务事实**，要"区分"不要"删除"——不要用脏数据考验检索模型，但也别把合法数据当脏数据删 |
| ❌ 混合检索万能 | ✅ "目前"是相对时间，BM25 字面匹配救不了，须先解析为绝对条件 |
| ❌ 分数高 = 答案对 | ✅ 相似文档间分数差 0.01 无判别意义，别拿阈值卡 |
| ❌ 都能靠检索解决 | ✅ 意图缺失时正确做法是**反问**，不是让检索去猜 |
| ❌ 元数据过滤是锦上添花 | ✅ 对可结构化属性是**主武器**，向量只是语义兜底 |
| ❌ Rerank 默认开启总没错 | ✅ +10ms 成本不一定值得（rag/SPEC 反模式）——先判"我面对的是质量歧义还是属性歧义" |

## 🔀 决策树

```text
用户问题 →
├─ 属性可结构化(时间/版本/规格/编号)？ → 【元数据过滤】主武器(pre-filtering)
├─ query 含精确属性词？               → 【混合检索】BM25 字面兜底 + RRF
├─ 意图缺失(用户没指定版本)？          → 【多路改写】或【反问】
└─ 多事实混在同一 chunk？             → 【结构化切分】前置修复
全链路：Rerank 只做最后的精度增强，不做事实仲裁
```
