# 「咬文嚼字」面试题格式规范 v1.0

> 本规范定义 `12.interview/**/*.md` 下所有 `.md` 面试题文件的统一写作格式。
> 适用范围：121 篇面试题（含 11.ai 下 14 篇、06.spring 下 14 篇等）。
> 适用对象：新写面试题、review 旧面试题、做 cheatsheet 自动化。

← [返回咬文嚼字 README](./README.md)

---

## 为什么需要规范
2026 系列扩到 121 篇 + 2026 路径整理后，写作格式逐渐分散：

- 32 篇原来没有场景开头的"概念速记式" / "TL;DR 速记式"
- 不同子模块（11.ai / 09.front-end / 04.system-design）用了不同模板
- split-hairs README 自标的 6 节模板（核心原理 / 代码示例 / 陷阱 / 最佳实践 / 面试话术 / 交叉引用）覆盖率约 70%

规范不是束缚创作，而是：
1. 让"高频面试题列表"自动生成（cheatsheet）
2. 让读者第一眼"掉进问题里"（场景开头强制）
3. 让 cross-ref 工作（与主模块 [18 个目录] 的引用网络保持一致）

## 文件结构（强制骨架）
按以下顺序排版，每节之间用 `---` 空行隔开：

| 区段 | 强制 | 用途 |
|------|-----|------|
| ① H1 标题 | **强制** | `# 标题 —— 一句话明确问题` |
| ② 一句话定位 blockquote | 推荐 | L3 `> 一句话定位：xxx —— 全篇 30 字点题`（11.ai 系列惯例） |
| ③ 系列定位块 | **强制** | `> 经典 X 面试题（Y、Z 高频）。考察的不是"…"，而是 **...** + **...** + **...**。` |
| ④（可选）上下文缩进 | 可选 | `⭐⭐⭐⭐ 深度级别`、`难度：⭐⭐⭐⭐`、`📚 前置知识：` |
| ⑤ 引子 | **✅ 强制** | 一个具体场景开场，详见 §2 |
| ⑥ 章节 1...N | 强制 | `## 一、核心原理`（默认），可省略变体见 §3 |
| ⑦ 面试话术 | 推荐 | `## X、面试话术（90 秒版本）` —— 一段可直接对答的术语 |
| ⑧ 交叉引用 / 相关章节 | 强制 | `## X、相关章节` —— 同栏目 + 主模块双向链接 |
| ⑨ 文末标注 | 可选 | `> 📅 YYYY-MM-DD · 咬文嚼字 · X主题 · ⭐⭐⭐⭐` |

### 完整骨架示例（基于已落地的 11.ai 系列）


### 关键约束

- **H1 标题**：必须明确问题（"为什么慢"、"3 大坑"、"X 是什么"），不能模糊
- **引子强制**：缺失引子 = 违反规范 = 不可 review 通过
- **章节最少 5 节**：核心原理 / 代码示例 / 陷阱 / 最佳实践 / 面试话术 中至少 4 节存在
- **结尾交叉引用**：必须指向主模块对应位置（**不允许** 死链接 / `./` 裸路径）

## 引子的 4 种合法场景类型
任何 `## 引子：xxx` 必须从下面 4 种选 1 种来构建（不可直接抛定义）：

### 2.1 生产 Bug（最推荐 50%+ 的题）

```text
🚨 凌晨 3 点告警：生产服务器 CPU 使用率 98%
```

**结构**：告警时间 + 现象 + 损失 + **疑问**。

### 2.2 反直觉代码（最推荐基础题）

```js
Integer a = 100; Integer b = 100; System.out.println(a == b);
```

跑出 true。但 `Integer a = 1000; Integer b = 1000` 却跑出 false。

**结构**：代码 + 反直觉现象 + **疑问**。

### 2.3 架构决策困境

```text
你有两台服务器做数据同步，网络突然断了——
```

CP（拒绝写入）还是 AP（两边都接受）？

**结构**：场景 + 后果对立 + **选择困境**。

### 2.4 性能对比（front-end / perf 题首选）

```text
第一次访问：2 秒
普通刷新：0.5 秒
再次访问：0.1 秒
```

**结构**：数字对比 + 提问"为什么差 20 倍"。

### 2.5 反例禁止

- ❌ "本文介绍 X 的原理..."（无场景）
- ❌ 直接列公式 / 列要点 / TL;DR 表格（缺铺垫）
- ❌ 只引用主模块一句话定位就完事（11.ai 系列旧的速记式）

## 章节命名规范
### 3.1 默认 6 节模板（推荐基线）

```markdown
## 一、核心原理（Why it works）
## 二、代码示例（Show me the code）
## 三、常见陷阱（What goes wrong）
## 四、最佳实践（Do this instead）
## 五、面试话术（How to answer in 30s）
## 六、交叉引用（Link back to main module）
```

### 3.2 已有的合法变体（保留）

各子模块已经有 4 种合法变体，新写时**按章节适配**：

| 子目录 | 章节模式 | 备注 |
|--------|---------|------|
| 11.ai 系列 | `## 一、核心原理` / `## 二、面试陷阱` / `## 三、最佳实践` / `## 四、面试话术` | 11.ai 系列的实际模板（不是默认 6 节）|
| 09.front-end `xxx/*README.md` | `## 一、核心结论（TL;DR）` + `## 二、详解` + `## 三、避坑指南` | "TL;DR 速记式"用于审题型短题 |
| 03.database SQL 调优类 | 同 09.front-end 的 TL;DR 模式 | 沿用既有规范 |
| 番外/管理类（已迁出） | 不再使用 | 见 README §4 保留边界 |

> 所有变体**必须保留 `## 引子：xxx`**，且**至少含 `核心原理 + 常见陷阱 + 面试话术` 3 节**。

### 3.3 数字编号强制

**所有章节标题用中文数字**：`一、二、三、四、五、六`
**禁止** "`第 1 章`" "`Chapter 1`" "`1.`" "`一、` 单独编号" 混用。

## 引用 / 衔接规范
- **同栏目链接**：`../xxx/README.md`（相对路径）
- **主模块链接**：`../../../xx/yy/README.md`（向上一两级，相对路径）
- **跨主模块链接**：`../../11.ai/...` 等
- **禁止**：绝对路径、纯文本 `02-xxx`、死链接、URL（GitHub blob）

### 反向链箭头规范（合法变体）

回链到父 README 的箭头**所有以下变体均合法**（自动化扫描脚本已全量兼容）：

| 变体 | 示例 | 适用场景 |
|------|------|----------|
| `←` (U+2190) | `← [返回: 父模块](../README.md)` | 主模块子文章（标准） |
| `⬅️` (U+2B05 + U+FE0F) | `⬅️ [返回: 父模块](../README.md)` | 12.interview/02.computer-basics/machine-learning/* 系列 |
| `⬅` (U+2B05, 无变体符号) | `⬅ [返回: 父模块](../README.md)` | 偶尔出现 |
| `→` (U+2192) | `→ [返回: 父模块](../README.md)` | 历史遗留，少量使用 |
| `🔙` (U+1F519) | `🔙 [返回: 父模块](../README.md)` | 极少见，保留兼容 |

**关键约束**：
- ✅ 箭头 + 空格 + `返回: <目标>` 三件套缺一不可
- ❌ 禁止 `←返回 [xxx]`（缺冒号）或 `[返回: ...]`（缺箭头前缀）—— 会被 `note-health` 单向链接扫描误报
- 🔧 **历史教训**（2026-08-31）：原扫描脚本只识别 `← [`，导致 12.interview/02.computer-basics/machine-learning/* 6 篇使用 `⬅️` 的文章全部误报，已在 `skills/note-health/references/structural-checks.md` 修复脚本（regex 扩展到 `⬅️ / ← / ⬅ / → / 🔙`）

### 反向链插入位置

- **默认**：放在 H1 标题块之后、一句话定位 blockquote 之前（与主模块子文章风格一致）
- **备选**：放在文件末尾（参考来源段落之后）

禁止放在 `## 引子` 内（会破坏场景铺垫节奏）。

## §5: 生产 Bug 类面试题特化（2026-08-28 沉淀实战新增）

> **触发**：用户提供真实生产事故案例（"线上 X 报警" / "X 100% 失败" / "X 反复触发"）—— 故事完整、有排查过程、有根因、有调优迭代。

### §5.1 命名约定（按现有先例排比）

| 主题类型 | 命名模板 | 已落地范例（参照排比） |
|---------|---------|------|
| 生产 Bug 排查类 | `<现象>-troubleshooting` | `cpu-spike-troubleshooting` / `metaspace-tuning-troubleshooting` / `no-class-def-found-troubleshooting` |
| 调优类 | `<对象>-tuning-troubleshooting` | `metaspace-tuning-troubleshooting` |

**原则**：命名按现有先例**排比**，不发明新格式。先 `ls 12.interview/<module>/` 看 3 个先例再命名。

### §5.2 7 节骨架模板（参照 cpu-spike-troubleshooting 强制结构）

```text
1. 引子（150-250 字真实场景，含具体堆栈 / 告警 / 数据）
2. 一、核心原理（含 3-5 个 WHY 反直觉点）
3. 二、排查方法论（5 步走，含 jstack / jstat / jcmd 工具命令）
4. 三、根因深挖（3-5 个反直觉点，必须有 ❌/✅ 对照）
5. 四、解决（含代码块 + 配置 diff + 前后对比）
6. 五、验证（制品层 / 环境层 / 应用层三角度）
7. 六、面试话术（90 秒版本，含关键词流）
8. 七、相关章节（≥ 3 条反向链 + ≥ 1 条同栏目兄弟链）
+ 文末 footer `← [返回: ...]`
```

### §5.3 Bonus 修复协议（沉淀时主动检查）

沉淀新案例时，**主动 grep 现有文件是否有同源反直觉错误**（同一错误示范）：

```bash
# 找现有文件中是否有同样的反直觉点
# 例：沉淀 MetaspaceSize 案例时，grep 找有没有其他文件只设 MaxMetaspaceSize 不设 MetaspaceSize
grep -rn "<本案例核心反直觉点关键词>" $KB_DIR/ | grep -v "<正常示范>"

# 找现有样例代码是否有相同错误
grep -B1 -A1 "<反模式关键词>=" $KB_DIR/<被链文件路径>
```

**判定**：
- 找到 1 处同源错误 → 顺手修复为单独 `fix(note)` commit（追加到本次沉淀的 commit 计划）
- 找到 2+ 处 → 评估是否批量修复（可能升级为单独任务）

### §5.4 当用户挑战"双层推荐"时的应对（2026-08-28 第一轮经验）

用户说"是不是只沉淀成面试题更合理？" → **不要直接相信**，做内部先例对照：

```bash
# 找同栏目 troubleshooting 类先例
ls $KB_DIR/12.interview/<module>/ | grep "troubleshooting"

# 统计行数（先例通常是 200-450 行）
wc -l $KB_DIR/12.interview/<module>/*troubleshooting*/README.md
```

| 判定 | 行动 |
|------|------|
| 先例 ≥ 3 篇且单篇 200-450 行 | **改推荐：单面试题版**（用户对） |
| 先例 < 3 篇 | 坚持双层推荐 + 解释为什么 |
| 内容是纯原理 / 跨多领域 | 拆分或走原决策树 |

**反模式**：看到用户挑战就立刻改方向（缺乏证据）—— 应该用先例数据支撑结论。
