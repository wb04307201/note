# 手搓 Agent vs 框架 —— 「框架太重」是现象不是理由

> 一句话定位：「框架太重」是现象不是理由——手搓 vs 框架不是站队，而是把**重在哪、代价是什么、你怎么权衡**拆成可量化决策。深度原理见 [主模块 框架源码对比与手搓 vs 框架决策](../../../09.ai-applications/agent/agent-architecture/framework-source-comparison.md)。

> **系列定位**：经典 AI Agent 架构选型面试题（2026 高频，Agent 团队几乎必问）。考察的不是"背结论说手搓好还是框架好"，而是 **抽象税的量化拆解** + **代价的分层归因** + **场景化权衡决策**。

---

## 引子：一句「框架太重」，被追问到哑口无言

```text
面试现场：某 AI Agent 创业公司二面——

面试官："你们为什么选择自己手搓 Agent，不用 LangChain？"
候选人（脱口而出）："因为 LangChain 框架太重。"
面试官（微笑）："哦？重在哪？"
候选人："呃……封装太多层……"
面试官："具体几层？每层干什么？代价是什么？"
候选人："……"
面试官（补刀）："Octomind 用了 LangChain 一年多最后弃用了，
                 你知道他们踩的坑和你们的一样吗？"
```

**「框架太重」是现象，不是理由**——就像"系统很慢"不构成性能优化的依据。说不出**重在哪、代价是什么、你怎么权衡**三问的答案，这个回答等于零分。

真实世界给出了两面的证据：

- **弃用派**：Octomind 用 LangChain 一年多，最终弃用——他们需要**动态调整可用工具**、观察/控制 Agent 中间状态，而 LangChain 没有任何机制暴露这些。Anthropic 官方也建议："框架为了通用需要很多额外抽象层，反而隐藏了最初的提示词，让你更难调试，出了问题连日志都看不明白。建议开发者直接调用 API。"
- **留用派**：某企业用框架几十分钟搭起工具调用 demo，自己写要几天；创业期"先证明能工作"比"架构完美"值钱十倍。

本篇把这句「太重」拆成可回答的工程语言。

---

## 一、三问检验：重在哪、代价是什么、你怎么权衡

「框架太重」必须通过三问检验，缺一问就是不及格答案：

| 三问 | 不及格回答 | 及格回答 |
|------|-----------|---------|
| **重在哪？** | "封装太多" | 调用栈 5 层类穿透、API 一年两换、提示词被藏进模板、中间状态黑盒 |
| **代价是什么？** | "性能差" | 延迟 2-5 倍（100ms vs 200-500ms）、Prompt Caching 失效烧钱、调试时间翻倍、升级即 breaking |
| **你怎么权衡？** | "所以不用框架" | 7 信号决策树：原型期用框架、生产核心链路手搓 |

**核心洞察**：手搓 vs 框架不是宗教战争，是一道**抽象税 vs 开发速度**的工程权衡题。你付的抽象税能不能换回等值的开发效率、生态复用、验证速度——这才是面试官要听的。

---

## 二、抽象税：框架的重到底重在哪

「重」不是安装包体积，是**抽象税（Abstraction Tax）**——为通用性付出的每一层间接。LangChain 的典型税单有 4 层：

### 税 1：调用栈层级（穿透 5 层才能改一行）

一次文本生成调用要穿过 **Chain → LLMChain → BaseLLM → BaseOpenAI → OpenAI** 5 层类。想改一个超时参数或加一个重试逻辑，先要理解 5 层各自的职责和继承关系。

```text
直接 API：
  client.messages.create(...)          ← 1 层，想改就改

LangChain（早期版本）：
  Chain → LLMChain → BaseLLM → BaseOpenAI → OpenAI
  ← 改个超时，先读 5 层源码
```

### 税 2：版本变动频繁（API 一年两换）

框架的通用抽象跟不上 LLM 生态演进，结果是**抽象层本身不稳定**：`Chain` 范式被 LCEL（LangChain Expression Language）取代，`create_react_agent` 又被 `create_agent` 替换。每次迁移都是全链路回归测试。

### 税 3：黑盒可观测（出了问题连日志都看不明白）

Anthropic 官方点评直指要害：框架为了通用加的抽象层**隐藏了最初的提示词**——你的 prompt 被模板拼装、被中间层加工，最终发给模型的和你写的不是一回事。生产排障时看不到真实请求/响应，等于盲调。

### 税 4：冗余提示词与缓存失效（税是按 token 计价的）

框架注入的包装性系统提示词、模板化上下文**改变 prompt 前缀**，导致 Provider 的 Prompt Caching 频繁失效——缓存的本质是前缀匹配，前缀一变全量重算。手搓则可以做到**前缀感知**：系统提示词和工具定义放前缀稳定区，动态内容放尾部，缓存命中率拉满。

## 三、代价对照表

把抽象税和手搓成本摆到同一张表上：

| 维度 | 框架（LangChain 类） | 手搓（纯 SDK + Agent Loop） |
|------|---------------------|---------------------------|
| **首次调用延迟** | 200-500ms | ~100ms（纯 API） |
| **调用栈** | 5 层类穿透 | 1 层 SDK 直连 |
| **提示词** | 模板拼装、黑盒 | 全程可见、前缀感知 |
| **Prompt Caching** | 易失效（前缀被改） | 可稳定命中（前缀分区设计） |
| **中间状态** | 无观察/控制机制（Octomind 弃用主因） | 实时插桩、动态修正 |
| **版本稳定** | API 一年两换（Chain→LCEL） | 只跟随 Provider SDK |
| **核心代码量** | 几十行配置 | LLM + Tool Router + Memory + Workflow Engine，几百行 |
| **上手速度** | 几十分钟跑通工具调用 | 自己写要几天 |
| **生态** | RAG/Memory/Vector DB/工具接口现成 | 逐个自建或选轻量库 |
| **适用阶段** | 原型验证 / demo / 中间层胶水 | 生产核心链路 / 强合规 / 性能敏感 |

**手搓的 3 个技术红利**（框架给不了的）：

1. **ReAct 循环绝对掌控**：每一步思考-行动-观察都能实时插桩、动态修正、按需注入上下文——Octomind 要的"动态调整可用工具"在手搓里就是改一个数组。
2. **上下文工程极致压缩**：前缀感知 + Prompt Caching 不失效 + 工具输出截断 + 对话历史折叠，token 成本可降一个数量级。
3. **流式交互与并发调度**：只读工具全量并发、写操作严格串行、超时中断——并发策略贴合业务而不是贴框架默认值。

**框架的 3 个不可替代场景**（手搓不划算的）：

1. **开发速度**：工具调用 + 记忆 + RAG 管道，框架几十分钟，手搓几天起步。
2. **生态成熟**：RAG / Memory / Vector DB / Tool 接口 / 模板全是现成积木。
3. **快速验证想法**：创业期第一目标是"证明能工作"，不是"架构可维护十年"。

## 四、决策树：什么时候手搓、什么时候用框架

7 个信号定生死（满足越多越倾向手搓）：

```text
Q1: 是否进入生产核心链路（影响营收/SLA）？
    ├── 是 → 手搓权重 +1        └── 否（原型/demo）→ 用框架，立刻收工

Q2: 是否需要精细成本控制（token 预算/Prompt Caching）？
    ├── 是 → 手搓权重 +1        └── 否 → 框架默认即可

Q3: 是否需要观察/控制中间状态（动态调工具/实时纠偏）？
    ├── 是 → 手搓权重 +2（Octomind 弃用框架的直接原因）
    └── 否 → 框架够用

Q4: 是否有强合规/数据安全要求（Prompt 与工具调用记录不能过第三方抽象层）？
    ├── 是 → 手搓权重 +1        └── 否 → 框架可接受

Q5: 是否性能敏感（延迟 100ms vs 500ms 有业务意义）？
    ├── 是 → 手搓权重 +1        └── 否 → 框架开销可忽略

Q6: 团队是否有能力维护 Agent Loop（几百行核心代码）？
    ├── 否 → 用框架 + 逐步剥壳  └── 是 → 手搓可行

Q7: 业务形态是"Agent + Workflow 混合"而非纯 Agent？
    ├── 是 → 手搓权重 +1（框架的纯 Agent 假设反而是负担）
    └── 否 → 框架模式匹配

判定：权重 ≥ 3 → 手搓核心循环（可借轻量库）；
      权重 1-2 → 框架起步 + 热点剥壳；
      权重 0 → 全框架，别浪费时间。
```

**典型映射**：机器人控制（每步可控 → 手搓）/ 金融风控 Agent（合规+审计 → 手搓）/ 创业 MVP（验证速度 → 框架）/ 内部工具（生态复用 → 框架）。

## 五、5 大手搓开源项目速记

手搓不等于从零造轮子——这 5 个项目是"手搓路线已被验证"的活证据，各学一个点：

| 项目 | 星数 | 一句话定位 | 学习点 |
|------|------|-----------|--------|
| **mini-swe-agent** | 7.5k★ | 普林斯顿出品，**约 100 行**核心代码在 SWE-bench 拿高分 | 手搓 Agent Loop 可以极简到 100 行——先跑通再演进 |
| **OpenAI Agents SDK** | ~3 万★ | Agent + Runner + Tool + Guardrail + Handoff 五件套 | 官方背书的"最小可用抽象"，比 LangChain 薄一个量级 |
| **Aider** | ~5 万★ | repo map 技术 + diff/udiff/全文件 3 种编辑模式 | 手搓到生产级的样子：上下文工程与代码编辑可以做到多精细 |
| **Goose** | 5.4 万★ | Block 出品，Rust 实现，MCP 深度集成 | 手搓不排斥标准协议（MCP）——协议是生态，框架才是税 |
| **PydanticAI** | 2 万+★ | 类型安全 + 依赖注入 + 结构化输出 | "框架派"的正确形态：薄、强类型、不藏提示词 |

> 速记口径：「100 行能上 SWE-bench，3 万星证明薄抽象有市场，5 万星证明手搓能到生产级。」

## 六、面试陷阱

### 陷阱 1：「框架太重」当结论说
- **真相**：「重」是现象不是理由。面试官听到这四个字的下一句必然是"重在哪？代价是什么？"。没有三问检验的回答是不及格答案——抽象税 4 层（调用栈/版本/黑盒/缓存失效）+ 代价对照（100ms vs 200-500ms）才是完整的工程语言。

### 陷阱 2：手搓 = 从头造轮子
- **真相**：手搓的是**Agent Loop 的控制权**，不是重写 HTTP 客户端。手搓照样用 Provider SDK、MCP 协议、PydanticAI 这类**薄库**——拒绝的是藏提示词的厚框架，不是一切复用。mini-swe-agent 100 行里一半也是调现成 API。

### 陷阱 3：「框架完全没用」
- **真相**：框架在**原型验证 / demo / 创业期"证明能工作"**阶段价值巨大——几十分钟 vs 几天。正确姿势是"框架起步、热点剥壳"：跑通流程后把性能/成本/可观测敏感的核心链路逐段换成手搓，而不是第一天就全手搓。

## 七、30 秒面试话术

> "我们的选型逻辑是把『框架太重』拆成三问来答：**重在哪**——抽象税 4 层，5 层类穿透的调用栈、一年两换的 API、被模板藏住的提示词、导致 Prompt Caching 失效的冗余前缀；**代价是什么**——纯 API 100ms 框架 200-500ms 的延迟、盲调排障时间、升级回归成本，Octomind 用了一年多最终因为没法动态调整工具、观察中间状态而弃用；**怎么权衡**——7 信号决策树：原型期用框架几十分钟跑通，进生产核心链路、要成本控制、要中间状态可控、强合规、性能敏感就手搓——LLM + Tool Router + Memory + Workflow Engine 几百行，照样借 MCP 协议和薄 SDK，像 mini-swe-agent 那样 100 行也能上 SWE-bench。
>
> 一句话：**框架付的是抽象税，买的是开发速度；税是否值回票价，取决于阶段和场景，不取决于信仰。**"
