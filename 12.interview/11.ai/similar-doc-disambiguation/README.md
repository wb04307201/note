# RAG 里同实体多版本/时序相似文档，如何精准区分？——为什么 Rerank 排不掉

> 一句话定位：时序/多规格下的多条相似文档是**合法事实**，不是脏数据；Rerank 是**精度增强**不是**事实仲裁**，排不掉属性级歧义——正确解法是把「语义模糊匹配」与「属性精确匹配」**解耦**。完整深度见 [主模块 相似文档消歧](../../../09.ai-applications/rag/similar-doc-disambiguation/README.md)。

> **系列定位**：RAG 检索工程面试题（AI 应用岗高频场景题）。考察的不是"会不会配 Rerank"，而是 **Rerank 的能力边界** + **属性歧义的工程化解法选型** + **解耦思维**。

---

## 引子：答错 10 倍金额的事故

```text
用户问："A项目目前的应收账款余额是多少？"
知识库里两条文档：
  Doc 1："截至 2026年11月，余额 120万元。"
  Doc 2："截至 2026年12月，余额 1200万元。"
RAG 系统把 Doc 1 检索进 Top-K，大模型答"120万"——差了 10 倍。
排查：上了 BGE-Reranker 也没用，Doc 1 打 0.92、Doc 2 打 0.93。
架构师问："Rerank 为什么救不了？这种多版本数据怎么检索才对？"
```

- **直觉解**："调调 Rerank 阈值 / 换个更强的 Reranker"——没意识到这是**能力边界**问题，不是调参问题
- **踩坑点**：把"多版本相似文档"当脏数据想清洗掉——但 11 月余额是合法历史事实，删了就丢审计口径

**题意边界**：问的是"**合理存在的相似文档如何区分**"，不是"脏数据怎么清洗"——答案的核心是语义/属性解耦。

## 一、核心原理

### 1.1 为什么 Rerank 排不掉

1. **语义平滑效应**：两条文档都在回答"应收账款余额"，全局语义匹配度都极高
2. **细粒度实体不敏感**："11月 vs 12月"、"120万 vs 1200万"在注意力空间的距离，远小于"应收账款 vs 余额"的主题词距离
3. **分数无判别意义**：0.92 vs 0.93（示意口径）——Rerank 无法识别"12月 = 目前"，错误数据留在 Top-K

**定位**：Rerank 对"同主题不同质量"有效，对"同质量不同属性"无判别力——它做精度增强，不做事实仲裁。

### 1.2 解耦原则 + 四类解法

**总原则**：向量模型理解"意思"；数字/时间/版本交给结构化或字面手段。

| 方案 | 解决的歧义类型 | 一句话做法 |
|------|--------------|-----------|
| **元数据过滤**（主武器） | 可结构化属性（时间/版本/规格） | 入库打 `{"time": "2026-12"}` 标签，检索前把"目前"解析成条件，pre-filtering 硬过滤 |
| **混合检索** | query 含精确属性词 | BM25 给"2026年12月"字面命中，RRF 融合兜底 |
| **意图澄清** | 用户意图本身缺失 | 多路改写（标准版/长续航版分别检索）或直接反问 |
| **Chunk 优化** | 多事实混在一个 chunk | 结构化切分，每 chunk = 自包含事实 + 上下文标题 |

## 二、面试陷阱

### 陷阱 1："Rerank 能排除错误数据"

- **❌ 错误解**："上更强的 Reranker / 调阈值就能把 11 月那条压下去"
- **✅ 真相**：属性级歧义是 Rerank 的能力边界——两条文档语义同样相关，分数差 0.01 无判别意义。答"Rerank 是精度增强不是事实仲裁，须语义/属性解耦"才到位

### 陷阱 2："多版本是脏数据，清洗掉就好"

- **✅ 真相**：时序/多规格并存是**合法业务事实**（历史余额要留审计口径）——目标是"精准区分"，不是"删到只剩一条"

### 陷阱 3："混合检索万能"

- **✅ 真相**：query 说"目前"，字面上没有"12月"——BM25 同样救不了**相对时间**。必须先把"目前"解析为绝对条件（`time == latest`），即元数据过滤先行

### 陷阱 4："都靠检索解决"

- **✅ 真相**：用户没指定版本时，歧义在**问题侧**——正确做法是多路改写或**反问**，不是让检索去猜

## 三、最佳实践

- **元数据为主武器**：入库期用 LLM/正则抽 `time/version/spec` 结构化标签（配 knowledge-ingestion-pipeline 的元数据规范）
- **相对时间先解析**："目前/最新/上季度"→ 规则或 LLM 转绝对条件，再进 pre-filtering（库内 `expr` 下推）
- **Rerank 只做最后增强**：+10ms 成本不一定值得——先判"面对的是质量歧义还是属性歧义"
- **度量口径**：黄金集标注"哪条是当前版本"，看 NDCG@K / MRR——"Rerank 前后无提升"正是盲区证据
- **姊妹题对照**：[Milvus Hybrid Search](../milvus-hybrid-search/README.md)（字面兜底的库内实现）/ [RAG 架构设计](../rag/README.md)

## 四、面试话术（30 秒 + 90 秒）

**30 秒版**：

> "多版本/时序相似文档是合法事实，不是脏数据。Rerank 排不掉它们——它做语义精度增强，不做事实仲裁，'11月 vs 12月'这种细粒度属性在向量空间里几乎无差异。正确做法是语义和属性解耦：向量管语义，数字/时间/版本交给元数据过滤——入库打结构化标签，检索前把'目前'解析成绝对条件做 pre-filtering。query 带精确词时 BM25 字面兜底；用户没指定版本时多路改写或反问。"

**90 秒版**（补纵深）：

> "先说现象：同一项目不同月份的余额、同一产品不同版本的参数，会在知识库里形成多条高度相似但属性不同的文档。用户问'目前的余额'，检索把 11 月那条一起召回，Reranker 两条都打 0.9 以上——因为 Rerank 有语义平滑效应，主题词层面它们同样相关，而'11月 vs 12月'、'120万 vs 1200万'在注意力空间的距离远小于主题词距离。所以指望 Rerank 或调阈值是死胡同，0.92 和 0.93 的差没有判别意义。
> 解法是解耦：把可结构化的'刺头'属性从文本里剥离。第一主武器是元数据过滤——入库时抽 time/version/spec 标签，检索前把'目前'这种相对时间解析成绝对条件，pre-filtering 硬过滤，库内通过 expr 下推，先过滤再召回。第二是混合检索：query 含'2026年12月'这类精确词时 BM25 字面命中、RRF 融合兜底——但注意相对时间 BM25 救不了。第三，歧义在问题侧时，多路改写或反问，比如续航里程没说版本，就拆成标准版/长续航版分别检索，或者直接问用户。第四是切分优化，保证每个 chunk 是自包含完整事实带上下文标题，别把两个版本的参数混在一起。
> 度量上用黄金集看 NDCG@K 和 MRR——一个很有意思的信号是：Rerank 前后指标没提升，恰恰证明这是属性歧义不是质量歧义。"

**延伸追问（含答案）**：

1. **Q：为什么不把旧版本数据直接删了，只留最新？**
   A：历史版本是合法业务事实——财务要审计口径、产品要历史参数对照。删数据丢信息，正确做法是打时间标签做**条件区分**（`time == latest` 只是其中一个条件，用户明确问"11月"时要能召回旧版）。
2. **Q：元数据提取不准（LLM 抽错 time/version）怎么办？**
   A：三层兜底——①正则先行（日期/版本号格式固定，规则比 LLM 稳）；②LLM 抽取 + schema 校验，置信度低的打 `uncertain` 标签走人工/降级；③黄金集持续回归，监控"属性正确率"指标。抽取失败的文档退回纯向量检索，不硬过滤。
3. **Q：反问和多路改写怎么选？**
   A：看**误答成本与交互频率**——高频低风险场景（商品参数）用多路改写 + 生成端综合列出，不打断用户；低频高风险场景（财务余额、医疗剂量）用反问，一次澄清换准确答案。可以按业务域配置策略，也可以置信度低于阈值才反问。
