# MQ消息积压

> **一句话定位**：MQ 积压 = 生产速率 > 消费速率，紧急扩容 + 异步化 + 监控告警三板斧，1 千万条也能救。

## 引子：消息队列堆了 1000 万条消息

```text
告警：RocketMQ 积压 1000 万条消息！
消费者处理速度：100 条/秒
生产者发送速度：10000 条/秒

→ 每秒增加 9900 条
→ 按这个速度，积压会越来越多
→ 磁盘满了 → 消息丢失 → 系统崩溃
```

消息积压的本质：**生产速率 > 消费速率**。

如果不处理，积压会像滚雪球一样恶化。

怎么排查？怎么解决？

---

## 一、消息积压的本质与影响
消息积压（Message Backlog）指消息生产者发送消息的速度持续超过消费者处理能力，导致未处理消息在队列中堆积。其核心矛盾是**生产速率 > 消费速率**，若未及时干预，积压会像滚雪球般恶化，引发以下后果：
- **系统性能下降**：资源（CPU、内存、磁盘I/O）被积压消息占用，导致新消息处理延迟。
- **业务风险**：核心业务（如订单支付）可能因消息延迟而失败，影响用户体验和收入。
- **数据丢失风险**：队列容量超限或消息过期时，数据可能永久丢失。
- **系统崩溃**：极端情况下，积压导致MQ服务不可用，引发服务雪崩。

## 二、消息积压的常见原因
### 1. 消费端问题（占比80%）
- **性能瓶颈**：
    - 消费逻辑复杂（如频繁调用外部接口、慢SQL查询）。
    - 线程池配置不合理（如线程数不足或阻塞）。
    - 消费者假死（如GC停顿、死锁、死循环）。
- **配置缺陷**：
    - 顺序消费中单条消息卡住，阻塞整个队列。
    - 广播模式重复处理导致效率低下。
- **故障**：
    - 消费者宕机或网络中断，无法拉取消息。

### 2. 生产端问题（占比10%）
- **流量激增**：
    - 突发大流量（如秒杀活动、定时任务集中触发）。
    - 补偿机制重发导致消息重复。
- **发送失控**：
    - 生产者线程池配置错误，发送速率远超预期。

### 3. Broker端问题（占比10%）
- **资源瓶颈**：
    - 磁盘I/O性能不足（如PageCache刷盘慢）。
    - 网络带宽不足或分区。
- **队列设计缺陷**：
    - 队列数量不足，无法充分利用消费者并行能力。

## 三、解决方案：紧急止血与长期优化
### 1. 紧急止血（临时方案）
**目标**：快速恢复消费速度，防止积压进一步恶化。
- **扩容消费者实例**：
    - 通过Kubernetes（HPA）或脚本动态增加消费者Pod。
    - **关键点**：确保消费者实例数 ≤ 队列数（如RocketMQ中，每个队列同一时间只能被一个消费者消费）。
- **开启批量消费**：
    - 修改消费者配置，一次处理多条消息（需实现幂等性）。
    - **示例**：`consumer.setConsumeMessageBatchMaxSize(10);`（RocketMQ）。
- **暂停非核心业务**：
    - 降低非关键业务消费者线程数，释放资源给核心业务。
- **消息转储**：
    - 将积压消息临时存储到数据库或文件系统，后续通过离线任务处理。

### 2. 长期优化（架构治根）
**目标**：提升系统吞吐量，预防积压复发。
- **优化消费逻辑**：
    - **异步化**：将耗时操作（如数据库写入、RPC调用）改为异步处理。
    - **批量操作**：合并数据库写入（如批量INSERT）减少I/O开销。
    - **代码优化**：使用Arthas或jstack定位慢代码段，优化线程池配置。
- **水平扩展**：
    - **消费者扩容**：根据业务峰值流量预估队列数，确保消费者实例数 ≥ 队列数 / 单实例线程数。
    - **队列扩容**：动态增加Topic的队列数（需确保Broker允许自动创建Topic）。
        - **示例**：`sh mqadmin updateTopic -n namesrv-ip:9876 -t order_topic -w 8 -r 8`（RocketMQ）。
- **限流与降级**：
    - **生产端限流**：通过令牌桶或漏桶算法控制发送速率。
        - **示例**：`producer.setSendMsgTimeout(5000); producer.setRetryTimesWhenSendFailed(2);`（RocketMQ）。
    - **服务降级**：在高峰期暂停非核心服务消息生产，或直接丢弃不重要消息。
- **优先级队列**：
    - 将核心业务消息设为高优先级，确保优先处理。
    - **示例**：RocketMQ支持18个延迟级别，可配置高优先级消息延迟更低。
- **死信队列管理**：
    - 将无法正常处理的消息转移到死信队列，避免阻塞主流队列。
    - 配置死信队列监控与告警，及时处理异常消息。

### 3. 监控与告警
**目标**：提前发现积压风险，实现快速响应。
- **关键指标监控**：
    - 待消费消息数：持续增长说明消费能力不足。
    - 最后一次消费时间：间隔过长代表消费者可能卡住。
    - 消费速度/生产速度比值：比值过低（如远小于1）说明积压风险高。
- **工具推荐**：
    - **Prometheus + Grafana**：采集MQ指标（如队列长度、消费延迟）并可视化。
    - **RocketMQ Dashboard**：实时查看消费者分组、队列分配、消费进度。
    - **ELK日志分析**：通过日志定位消费慢的原因（如慢SQL、外部接口超时）。
- **阈值告警**：
    - 设置待消费数超过1万、消费延迟超过5分钟等阈值，触发邮件/钉钉/微信告警。

## 四、实战案例：电商大促消息积压处理
**场景**：电商大促期间，订单系统消息积压20万条，导致用户支付后订单状态更新延迟。
**处理步骤**：
1. **紧急止血**：
    - 动态扩容消费者实例至50个（原10个），充分利用队列资源。
    - 开启批量消费，每次处理10条消息。
    - 暂停非核心业务（如日志采集）消费者，释放资源。
2. **长期优化**：
    - 优化消费逻辑：将订单状态更新操作改为异步，减少数据库锁竞争。
    - 水平扩展：增加Topic队列数至100个，确保消费者实例数 ≥ 队列数 / 单实例线程数（20）。
    - 限流：对生产者进行限流，确保发送速率不超过消费者处理能力。
3. **监控加固**：
    - 配置Prometheus + Grafana监控待消费数、消费延迟等指标。
    - 设置阈值告警，待消费数超过5000条时触发告警。

## 五、预防性建议
1. **压测与演练**：
    - 使用JMeter或LoadRunner模拟峰值流量，验证消费者处理能力。
    - 定期进行混沌工程演练，注入消息处理延迟，测试系统容错性。
2. **SLA设计**：
    - 定义消息类型积压阈值与处理策略（如支付订单 > 1000条自动扩容 + 短信告警）。
3. **灰度与回滚**：
    - 消费逻辑变更时，新版本消费者订阅新Topic，逐步切流（如10% → 50% → 100%）。
    - 异常时秒级切回旧版本，避免影响生产环境。

## 六、常见陷阱

### 陷阱 1：消费者实例数 > 队列数的无效扩容
- **真相**：RocketMQ/Kafka 里**一个队列同一时间只能被同组内的一个消费者消费**。队列只有 16 个却扩到 50 个消费者实例，多出来的 34 个实例分不到队列，**完全空转**——第四节案例中扩容前先把队列数提到 100 正是为此。扩容顺序必须是：先看队列数够不够（`mqadmin updateTopic` 扩队列），再扩消费者。

### 陷阱 2：顺序消息为了提速改并行消费，结果乱序
- **真相**：积压时最容易犯的错——把顺序消费改成并发消费提速。订单"创建→支付→发货"三条消息被不同线程乱序处理，业务状态直接错乱。顺序消息积压只能**横向扩队列 + 保持队列内串行**，或临时转储后按序重放；第二节提到的"顺序消费中单条消息卡住阻塞整个队列"，解法是把卡住的消息挪进死信队列，而不是放弃顺序性。

### 陷阱 3：消息转储后重放不做幂等，造成数据重复
- **真相**：第三节"消息转储"（把积压消息临时存 DB/文件，事后离线重放）是有效的止血手段，但 MQ 本身是 at-least-once 投递，转储和重放过程都可能重复处理同一条消息。消费端没有幂等保障（唯一键约束 / 去重表 / 状态机校验），重放一次就多扣一次库存、多发一次通知——救火变成放火。开启批量消费（`setConsumeMessageBatchMaxSize`）同理，正文特意标注"需实现幂等性"。

### 陷阱 4：只盯"待消费消息数"一个指标
- **真相**：待消费数持续增长固然说明消费能力不足，但"最后一次消费时间间隔过长"才能发现**消费者假死**（GC 停顿、死锁、单条消息卡住）——此时待消费数上涨反而可能被误判为流量问题。第三节监控要求三个指标一起看：待消费数、最后消费时间、消费/生产速率比。

## 七、面试话术

### 30 秒版

> "MQ 积压的本质是生产速率持续大于消费速率。我的处理框架是三板斧：**紧急止血**——扩容消费者（注意实例数不能超过队列数）、开启批量消费、暂停非核心业务、必要时把积压消息转储离线处理；**长期治根**——优化消费逻辑（异步化、批量写库）、扩队列扩消费者、生产端限流、死信队列兜底；**监控预防**——待消费数、消费延迟、消费/生产速率比三个指标 + 阈值告警，压测验证消费能力。回答时强调消费者数 ≤ 队列数这个约束和消费幂等，是拉开区分度的点。"

### 90 秒版

> "先定位原因再动手。积压三大来源：**消费端占 80%**（慢 SQL、外部接口慢、线程池配置不当、消费者假死）、生产端 10%（秒杀等突发流量、补偿重发）、Broker 端 10%（磁盘 I/O、队列数不足）。排查靠 RocketMQ Dashboard 看消费进度 + Arthas/jstack 定位慢代码段。
>
> **紧急止血**四招：① 扩容消费者实例——但有个关键约束，一个队列同一时间只能被一个消费者消费，实例数超过队列数就是空转，所以必要时先 `mqadmin updateTopic` 扩队列；② 开启批量消费，一次拉 10 条，前提是消费逻辑幂等；③ 暂停非核心业务消费者，把资源让给核心链路；④ 积压太深就把消息快速转储到 DB/文件，新建临时 Topic 扩队列重放。
>
> **长期优化**：消费逻辑异步化 + 批量 INSERT 减少 I/O；按峰值流量做容量规划（队列数 ≥ 消费者实例数 × 单实例线程数的匹配）；生产端令牌桶限流；核心消息走优先级队列；异常消息进死信队列避免阻塞主队列。
>
> **监控告警**：Prometheus + Grafana 盯三个指标——待消费消息数、最后一次消费时间（识别假死）、消费/生产速率比，设阈值（如待消费 > 1 万、延迟 > 5 分钟）自动告警。预防靠压测演练 + SLA 分级（支付类消息 > 1000 条自动扩容）+ 消费逻辑变更灰度切流。"
