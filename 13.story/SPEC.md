#### 判定信号表（6 信号，前 3 为核心）

| # | 信号 | 判据 | 权重 |
|---|------|------|------|
| ① | **人物弧** | 主题能承载「决策 → 踩坑 → 代价 → 翻盘」的人的故事（老板/团队/职业），而非纯机制解释 | 核心 |
| ② | **类比落地** | 能找到 5 岁能懂的核心厨房比喻（对应 D4 易懂性的前置测试） | 核心 |
| ③ | **❌/✅ 事故** | 有真实/可信的事故场景可戏剧化（对应 D3 反例对比的前置） | 核心 |
| ④ | **受众匹配** | 价值在「理解全局」（系统学习者/管理者）而非「面试对答」（后者归 12.interview） | 加权 |
| ⑤ | **体量支撑** | 主题撑得起完整起承转合（≥300 行主线章），或明确走「联动短章」形态 | 加权 |
| ⑥ | **系列定位** | 能作为前传/续集/番外插入现有叙事弧（对照 `index.md`），不产生孤儿 | 加权 |

**判定规则**：①②③ 全过 + ④⑤⑥ 至少 2 过 → 走三层联动（主线章）；①②③ 过但 ④⑤⑥ 弱 → 只做双层（主模块 + interview），story 不动或仅作短章联动。

#### 两种合法形态

| 形态 | 体量 | 特征 | 代表章节 |
|------|------|------|---------|
| **主线章** | 300-900 行 | 完整起承转合 + 高叙事密度 | 01-27 章群（60-97 次阿明/千行） |
| **联动短章** | 150-300 行 | 叙事封面 + 尾部链 interview/主模块配套内容 | 42-47 章群（`45 番外九` → skill-hit-rate） |

> 联动短章是 v2.x 起追认的合法形态（2026-10 之前按主线章标准衡量会被判「体量不足」，但三层联动价值真实）。

## §4 强骨架格式规范

> 本节原为独立文件 `STORY-FORMAT-SPEC.md`（v1.0，2026-06-30）。v2.0（2026-09-26）合并入主 SPEC.md，本文件升级为 L1 完整模块规范。

### §4.1 为什么需要规范

2026 年系列扩到 46 篇后，写作格式逐渐分散。`README.md`、`index.md`、`cheatsheet.md`、`glossary.md` 都依赖统一的标题与编号体系。规范不是束缚创作，而是让**检索、引用、自动化（cheatsheet 生成、交叉引用、mermaid 拓扑）**不被"作者当时的笔兴"拖累。

### §4.2 文件命名

```text
[两位数编号]-[英文主题-slug].md
```

- **编号固定**，前导零（`01`、`02` ... `46`）。
- **孪生篇**：`34a` / `34b`、`35a` / `35b`、`36a` / `36b`。
- 主题 slug 用英文小写 + 短横线，不含中文。
- 编号一旦分配**永不重用**；废弃稿件不删号、不补号。
- **文件名前缀是全系列唯一的编号权威**。H1 的 `# NN ·`、frontmatter 的 `number`、
  以及正文 / 索引 / 术语表里所有引用，都**必须**与文件名前缀一致。
  - 背景：早期两次章节合并（原 17 并入 `19-realtime-eventdriven`、原 23 并入 `22-database-migration`）
    使叙事号整体前移 +1 / +2，但 H1 未跟随，导致 30 篇 H1 与文件名系统性不一致。
  - 2026-10-11 已按本规则全量对齐（30 H1 + 172 链接文本 + 39 裸 slug + 7 处孪生篇编号族）。
  - 新增篇章时：写完先 `ls 13.story/` 取最大编号 +1，**文件名、H1、frontmatter 三处同时落同一编号**。
- 文件名一旦定稿，**文末 `← [返回系列导读]`、`index.md` 链接、`glossary.md`索引**必须同步更新。

### §4.3 文件结构（强制骨架）

按下列顺序排版，每节之间用 `---` 空行隔开：

| 区段 | 强制 / 推荐 | 用途 |
|------|-----------|------|
| ① 编号标题 | **强制** | `# 编号 · 标题`（无编号永不通过 review） |
| ② 一句话副标题 | 强制 | `> 从阿明...，看... —— 一句话点题` |
| ③ 系列定位块 | **强制** | `> **系列定位**：本篇是「阿明餐厅」系列的**[位置]**...` |
| ④（可选）兄弟篇块 / 合并说明 / 写给 X 的一句话 | 推荐 | 见 §4.4 |
| ⑤ 引言 | **强制** | `## 引言：xxx`（**全文唯一**） |
| ⑥ 章节 1...N | 强制 | `## 第一章：...` / `## 0 第零章：...`（见 §4.5） |
| ⑦（可选）总结表 | 推荐 | 当章节 ≥ 5 时，给一张"目录速查表" |
| ⑧ 延伸阅读 / 跨章节衔接 | 推荐 | 见 §4.6 |
| ⑨ 结尾回链 | **强制** | `← [返回系列导读](./index.md)`（独占一行，可在前置 "📅" 标注后追加） |

#### 完整骨架示例

```markdown
# 47 · 一句话标题

> 一句话副标题 —— 用阿明的场景点题

> **系列定位**：本篇是「阿明餐厅」系列的**[位置]**。

---

## 引言：一句话引言标题

开篇故事段落。用 1-3 段建立"阿明的某次真实场景"。

---

## 第一章：xxx —— xxx（em dash 副标题）

小节标题：`### 1.1 xxx`

---

## 延伸阅读

- [`02-system-architecture-evolution`](./02-system-architecture-evolution.md) —— 一句话点连接理由

---

- [QUESTION-FORMAT-SPEC](../12.interview/SPEC.md#§4-强骨架格式规范)
← [返回系列导读](./index.md)
```

### §4.5 章节体系

#### §4.5.1 主流结构（强制默认）

- 引言：`## 引言：xxx`（**全文唯一**）
- 章节：`## 第一章：xxx —— xxx` （em dash 副标题，可省略）
  - 子节：`### 1.1 xxx`
- 终章：`## 终章总结：一句心法` 或 `## 一句心法：xxx`

> 使用「第一章」「第二章」的中文数字，与 README、cheatsheet、引述块保持一致。**禁止**"`第 1 章`" "`Chapter 1`" "`一、`" "`第 1 节`" 混用。

#### §4.5.2 戏剧结构变体（仅 `03-refactoring-guide-for-pm.md`）

番外一是 PM 受众，叙事节奏要"用户故事"。允许：

- 取消 `## 第一章` 体系
- 改用 `## 五幕剧：当"加新菜"遇到"旧厨房"` 风格
- 子幕：`### 第一幕：xxx`、`### 第二幕：xxx` ...

> 其他文件**不允许**模仿，避免结构泛滥。变体如要复用，需在 PR 里单独标注说明理由。

#### §4.5.3 续集 18-20 戏剧体（44 / 45 / 46）

由于这 3 篇谈"事故 / 复盘 / 职业"，叙事性强，允许"开场 + 第一幕 + 第二幕"结构：

```markdown
### 一、开场：（承担"## 引言"的角色 —— 一个具体场景或人物出现）
### 二、第一幕：...
### 三、第二幕：...
### 四、第三幕：...
### 九、相关章节
```

**关于 `## 引言`**：

- §4.5.1 主流结构：`## 引言：xxx`（紧跟标题块）→ `## 第一章` ...
- §4.5.3 戏剧体（44/45/46）：**可省略 `## 引言`**，`### 一、开场：xxx` 段代替它承担"场景铺垫"角色

两种合规，但**单篇文章只能用一种**（要不就 `## 引言` + `## 第一章`，要不就 `### 一、开场` + `### 二、第一幕`，混用不通过）。

但 **H1 仍必须** `# NN · 标题` 这种编号 + 间隔点格式；编号不可丢。

#### §4.5.4 第零章特例（仅 `33-ai-fatal-trio.md`）

`33` 因为 "5 分钟快速概览" 是亮点，**第零章合法**：

```markdown
## 引言：3 起看似无关的 AI 事故，背后是同一组漏洞

## 第零章：5 分钟快速概览 —— 三件套是什么，为什么致命

## 第一章：xxx
```

数字 0 是允许的特例（只在"概览 / 前置"用途），其他文件不要用。

#### §4.5.5 引言重复的反例

**全文只允许一个 `## 引言：...`**。常见错误写法（已被修复 6 处）：

```markdown
## 引言：...                                ← 第 1 次 OK

> **阿明的厨房类比（开篇场景）**：...

## 引言：...                                ← 第 2 次 ❌ 重复

<正文>
```

正确写法：

```markdown
## 引言：...                                ← 全文仅一次

> **阿明的厨房类比（开篇场景）**：...     ← 类比块直接跟随

<正文>
```

#### §4.5.6 章节编号硬约束（🆕 2026-09-01，D3 评分依据）

**主结构（§4.5.1）文件必须**：

- 章节标题：`## 第一章：xxx` / `## 第二章：xxx` / `## 终章总结：xxx`
- 子节标题：`### 1.1 xxx` / `### 1.2 xxx`
- 中文序数 + 阿拉伯数字混用

**允许的偏离（必须显式标注例外）**：

| 例外类型 | 适用范围 | 标记方式 |
|---------|---------|---------|
| 戏剧结构（§4.5.2）| 仅 `03-refactoring-guide-for-pm.md` | 文件首部注释 + README 标注 |
| 续集戏剧体（§4.5.3）| 仅 44 / 45 / 46 | 文件首部注释 + README 标注 |
| 第零章（§4.5.4）| 仅 `33-ai-fatal-trio.md`（5 分钟快速概览）| 文件首部注释 + README 标注 |
| 番外 | 32 / 34 等"番外 N"系列 | frontmatter `position: 番外 N` |
| 终章 | 任何文件可加"## 终章总结"作为压轴 | frontmatter `position: 主线` + H1 编号 |

**违规检测**：

- `note-health` D3 评分（章节编号规范）：0-2 分
- 0 分场景：混用「Chapter 1 / 第 1 章 / 一、」三套系统
- 1 分场景：基本一致但偶有偏离
- 2 分场景：完全符合上述规范或显式标注例外

#### §4.5.7 系列定位块体量要求（🆕 2026-09-01，D5 评分依据）

**`> **系列定位**：...` 块必须 ≥3 行段落级**，禁止单句话。

**正确写法**：

```markdown
> **系列定位**：经典 AI 架构面试题（架构师级 / 100% 命中）。
> 考察的不是"Memory 是什么"，而是 **三维分类体系的完整度**
> + **场景适配的选择能力** + **业界框架的能力边界**。
```

**违规反例**：

```markdown
> **系列定位**：AI 工程师必看        ← 仅 1 句，不达标
```

**违规检测**：

- `note-health` D5 评分：≥3 行 = 2 分；1-2 行 = 1 分；0 行或仅 1 句 = 0 分
- 历史教训（v3 抽样 2026-09-01）：42 / 43 / 44 / 45 / 46 五篇均仅 1 句，被标 D5=1
- 修复建议：将单句扩展为"经典 + 考察维度 1 + 维度 2 + 维度 3"四段结构

### §4.6 引用 / 衔接章节

- **统一名称**：单数文章用 `## 延伸阅读`（主流做法）。
- **孪生篇**：除延伸阅读外，可在文末追加 `## 跨章节衔接`，专门指向孪生篇 /外部引用文章。
- **续集 18-20**（44 / 45 / 46）：用 `### 九、相关章节` 命名。
- 项目内引用一律相对路径：`./02-system-architecture-evolution.md`；
  禁止绝对路径、禁止裸 `02-...` 文本链接。
- 外部路径（跨主模块）：`../11.ai/...`。

### §4.7 载体规范（代码块 / 表格 / mermaid）

#### §4.7.1 代码块

- 必须用 ```` ```text ```` / ```` ```mermaid ```` / ```` ```python ```` / ```` ```sql ```` 等语言声明
  包围，**禁止裸 ```` ``` ````**。
- 任何代码注释不得在 Markdown 中裸写为 `# xxx`，会被 Grep / 渲染器误识别为
  H1。当前在 `11 / 13 / 16 / 18 / 19 / 20 / 21 / 22 / 30` 等多个文件存在该
  历史问题，未来迁移时统一修复。
- 当代码用于表达架构图（如责任金字塔）时，**优先用 `mermaid`**：

    ````markdown
    ```mermaid
    graph TD
      A[顶层：架构师] --> B[中层：SRE] --> C[基层：业务工程师]
    ```
    ````

#### §4.7.2 表格

- 表头与 `|------|` 对齐可选（Markdown 渲染无要求）。
- 但同一系列内应保持一致 —— **统一使用"冒号对齐"**（左对齐），便于
  Prettier 等工具格式化。
- 表格内字符数较多时，首列做"主语 + 链接"，后续列做"解释"。

示例：

```markdown
| 模块 | 核心问题 | 餐厅类比 | 技术实现 |
|------|----------|----------|----------|
| 感知层 | 听懂用户要什么 | 翻译官 | 多模态 + 意图识别 |
```

#### §4.7.3 mermaid 图

- `graph` 方向：`TD`（自顶向下）优先于 `LR`（自左向右）。
- 每个故事**最多 3-4 张 mermaid**，避免图表通胀。
- 节点 label 加双引号或 `<br/>`，**禁止未引用就 `subgraph`**。

### §4.9 frontmatter（story 类型）

为了让 `cheatsheet.md` 等自动工具能解析，建议在文末 `← [返回系列导读]`
之前追加 HTML 注释 frontmatter：

```markdown
<!--story:
  number: 42
  title: AI 替你写代码，谁替系统负责？
  type: 续集
  position: 续集十八
  sibling: null
  audience: CTO / 技术管理者 / AI 工程师
  core_concepts: [系统责任金字塔, AI协作工程师, AI SRE, AI 安全审计师]
  status: active
-->
```

不强制，但加上后便于静态扫描脚本产出 cheatsheet。
字段对齐详见全局 [`SPEC.md` §4](../SPEC.md#四-frontmatter类型) frontmatter 类型。

> ⚠️ **`number` 必须等于文件名前缀**（如 `42-ai-engineer-responsibility.md` → `number: 42`）。
> 2026-10-11 全库对齐时发现 `45-skill-scheduling-restaurant.md` 用的是旧 `13.story` 时代的
> `id:` schema（值还是 `47-skill-scheduling-restaurant`），已迁移到本 schema。
